# 项目需求：会议室预订系统（meeting-room，中型全栈项目）

> 冻结输入。功能如下，技术选型、UI 框架、界面风格由你决定——
> 唯一的交付约束：前后端都要能用 npm 一键安装/启动/构建（Node 生态）。

## 目标

给一个 30 人的办公室做会议室预订：看有哪些房间、订某个时间段的房间、
查看/取消自己的预订、看本周和统计。前后端 + 数据库齐全。

## 功能清单

1. **会议室管理**：新增（名称、位置、容量、是否带投影/白板）、修改、删除（有未来预订的房间不许删，返回 409）、列表。
2. **发起预订**：选房间 + 日期 + 起止时间 + 预订人姓名。
   - 结束时间必须晚于开始时间，非法返回 400；
   - **时间冲突硬校验**：同房间已有预订与新区间重叠时返回 409，绝不允许双重预订；
   - 跨中午/跨小时的长时段合法（只要不与已有预订重叠）。
3. **预订查询**：按房间 + 日期范围查（返回该房间的时段列表）、按预订人查。
4. **取消预订**：删除预订并释放时段；取消后同一时段可以再次被订成功。
5. **周视图**：给定任意一天，返回该日期所在周（周一到周日）每天的预订数量与时段明细。
6. **使用统计**：每个房间的预订总数与累计预订时长（分钟），按总时长降序排列。

## 接口约定

- REST + JSON，前缀 `/api`；资源至少包含 `/api/rooms`、`/api/bookings`、`/api/bookings/week`、`/api/stats/rooms`；
- 成功 200/201，参数非法 400，资源不存在 404，时间冲突 409；
- 无登录系统：预订人就是一个姓名字符串。

## 报文与验收前置约定（供机器验收比对，字段名照此实现）

- 创建房间：`POST /api/rooms`，请求体 `{"name":"...","location":"...","capacity":12,"hasProjector":true}` → 201，响应体含自增数字 `id`；
- 创建预订：`POST /api/bookings`，请求体 `{"roomId":1,"date":"2026-09-18","start":"10:00","end":"11:30","bookedBy":"..."}` → 201；
- 重叠预订：同房间与已有时段重叠 → 409；
- 取消：`DELETE /api/bookings/{id}` → 200；
- 周视图：`GET /api/bookings/week?date=YYYY-MM-DD` → 200，返回周一~周日每天的预订数量与明细；
- 统计：`GET /api/stats/rooms` → 200，数组按累计时长降序；
- 验收从**空库**开始、造数据全走 API：因此首个创建的房间 `id` 为 1，后续断言按此引用。

## 前端页面

- 四个页面：房间列表（含新增表单）、发起预订（表单 + 冲突时把 409 的错误友好展示出来）、我的预订（按预订人查 + 取消按钮）、周视图（7 天网格或列表）；
- **视觉要求**：布局与配色必须自成一体（例如左右分栏 + 侧边导航的后台风格），
  **不许做成"单张居中卡片 + 上下列表"的极简清单样式**——上一轮就是这个样子，要换；
- 所有后端调用走 `/api` 前缀；API 不可达时页面骨架仍要能渲染，不许白屏。

## 验收期望（必须真实可执行）

- 上述接口按真实调用验证：创建房间 201、正常预订 201、**重叠预订 409**、
  取消后重订同时段 201、周视图数字与造的数据逐一对得上；
- 前端 `npm run build` 成功；后端 `npm start` 一键启动、监听 `PORT` 环境变量；
- 首屏渲染非白屏，页面文本包含「会议室」。

## 边界（本期不做）

- 不做登录/注册/权限；不做邮件/消息通知；不做分页；不做秒级精度（最小粒度 30 分钟）；
- 不引入外部服务（消息队列/缓存/搜索引擎一律不用），数据库用嵌入式的即可。
