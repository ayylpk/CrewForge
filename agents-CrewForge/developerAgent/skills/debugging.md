# Skill: debugging

> 指导材料。不能改变权限、Graph 结构、Contract、验收标准、Ledger 或预算；**不能写盘**。

## 何时加载

收到 `test_failure`，进入修复循环时。

## 做什么

### 第 0 步（最重要）：先把"红色信号"跑出来，再谈原因

**在能一条命令复现这个失败之前，不读代码猜原因**——猜出来的是故事，不是根因。
【实录 s4：PATCH 一族 500/404，模型没有先构造红色回路而是批量重写 17 个文件，
把已通过的接口也改挂——无回路的修复 = 回归制造机】

1. 先构造一个**可重复、可判红**的回路：重跑失败的那条命令 / 一条 curl / 一段最小脚本 /
   一个失败用例。要求：① 能因**这个** bug 变红；② 每次结果一致；③ 几秒内出结果。
2. 回路跑红了，再把场景**缩到最小**：逐个砍输入、砍调用、砍配置，每砍一刀重跑一次，
   只留下"删掉它就不红了"的部分。
3. 只有在拿到这条红色回路之后，才进入下面的排查。

> 若确实构造不出回路：**停下来说明**，列出试过的方法，向外部要环境/日志/证据——
> 不要在无回路的情况下继续推理（那正是这一条要防的事）。

### 拿到回路之后

4. **先读完整证据**：category、command、args、cwd、exitCode、stdout、stderr、affectedFiles
   —— 这是机器原样回传的，不是摘要；被截断时会附带原始输出的落盘位置，必要时让
   Developer 用 `readFile` 打开它；
5. `readFile` 打开 affectedFiles 的**当前**内容（不是记忆里的版本）；
6. `gitDiff` 看刚才那次改动到底改了什么；
7. **用命令复现**，而不是推理：
   - 重跑失败的那条命令（`runCommand` / `shell`），看真实退出码；
   - 需要长时间观察的服务用 `startProcess` 起，再 `readProcess` 读增量日志
     （**不要**反复重启同一个服务）；
   - 接口类问题用 `httpRequest` 打 `127.0.0.1` 上的真实接口，看状态码与响应体；
   - 直接跑一小段脚本验证猜想（用**本项目栈**对应的运行时）；
8. 排查时一次只改一个变量；如果要加临时日志，给日志打一个唯一前缀（如 `[DBG-a4f2]`），
   修完按前缀一次清干净——没打标记的日志会活下来污染代码；
9. 按 category 定向排查：
   - `COMPILE` → 语法 / 类型 / 导入 / 依赖缺失；
   - `BOOT` → 配置、端口占用、依赖注入、启动顺序；
   - `MIGRATION` → 建表语句、字段类型、库连接；
   - `CONTRACT` → 路径 / 方法 / 请求体 / 状态码与契约不符；
   - `RENDER` → 页面白屏、路由漏注册、字段名不匹配；
   - `ENV` → 环境缺失（这类不是改代码能解决的，如实上报）；
10. 定位到**根因**再动手，一次只改一处；
11. 改完重新跑**同一条失败命令**，看它是否真的变绿——再把第 0 步那条原始回路对一遍，
    确认原场景也不再复现。

## 判断纪律

- 同一个 `failureSignature` 反复出现 → 说明上次的修法不对，**换方向**，不要原样重试
  （实录 s4：PATCH 探测 5 次全是 500，原样重试零价值）；
- 改了文件但错误一字不变 → 停下来分析，不要第三次重试；
- 同一条命令**连续超时两次** → 已经标记 `TIMEOUT_REPEATED`，停手并上报，
  先判断是环境/依赖问题而不是再等一次超时；
- 拿不准、或证据交叉在三个以上文件 → 用 `delegateReadonly` + `role:"debugger"`
  调只读子 Agent（机器证据由系统自动注入，`question` 里写清楚要分析什么）。

## 只读子 Agent 的使用口径

1. 它是**分析助手不是裁判**：返回 `{rootCause, evidence, recommendedChanges, risks,
   confidence, cannotVerify}` 结构，`readonly` 由程序固定为 true，权威字段回不来；
2. 同一 `failureSignature` 系统只让你调一次；返回带 `stale:true` 时旧结论只作参考；
3. 采纳前必须核实：它引用的 `path:line` 用 `readFile` 打开对一遍；
4. 它的"可能/优先核对"是**线索不是结论**——`confidence:low` 或 `cannotVerify` 里的
   内容不得当作根因写进修复动作；
5. 修复动作、重跑命令、落盘，全部由你（Developer）执行；它没有也没有这些能力。

## 禁止

- 禁止改测试、改断言、改验收标准来让错误消失；
- 禁止删掉失败用例、跳过用例；
- 禁止在没有新证据的情况下重复提交同一个修复；
- 禁止把"我改了应该就好了"当成验证——必须看到命令真的退出码为 0。
