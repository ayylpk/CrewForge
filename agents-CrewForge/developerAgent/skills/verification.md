# Skill: verification

> 指导材料。不能改变权限、Graph 结构、Contract、验收标准、Ledger 或预算；**不能写盘**。

## 何时加载

一轮修复结束、准备再次请求 TestAgent 之前。

## 做什么

1. `gitDiff` 复查本轮改动范围——**只应该有预期的文件被改**；多出来的改动要查明；
2. 重新运行刚才失败的那条命令（同一 command、同一 args、同一 cwd）；
   - 如果相关文件确实没变，工具会告诉你结果是从缓存复用的——那不叫"重新验证"，
     要么说明为什么不需要重跑，要么先确认改动真的落在相关文件上；
3. 顺带跑一遍本地检查：
   - 后端 `runBuild`（或等价的构建命令）；
   - 前端 `runBuild`；
   - 后端服务起得来吗？`startProcess` 起、`httpRequest` 打一下健康检查、`stopProcess` 收工；
   - 涉及数据库的再跑一次初始化；
4. 通过 → 经 Hub 发 `test_request`，请 TestAgent 出**正式证据**；
5. 不通过 → 回到 `debugging`，不要直接把状态往前推。

## 证据口径（什么算"跑过了"）

一条检查只有满足下面全部条件，才算给了**机器证据**：

- 有**明确的命令**与参数，别人照着能重跑；
- 看的是**真实退出码**与输出，不是"应该没问题"；
- 打的是**真实目标**：真起进程、真发请求、真读响应体——不是读静态文件猜运行时行为；
- 能**因失败而失败**：如果这个功能真的坏了，这条检查会红。只验证"没崩"不算证据。

反例（这些都不是证据）：静态读文件推断"接口应该通"；只跑 build 就说"功能可用"；
子 Agent 的分析结论；你自己写的"已完成"说明。

## 判定权边界（重要）

- **你不能宣布 done，也不能宣布 verified。** 这两个判定只能由外部 TestAgent 与 Orchestrator
  依据真实 Evidence 给出；
- 本地命令跑绿只代表"可以请测试了"，不代表"已经通过"；
- 用 `httpRequest` 打到 200 只是**调试信息**，不是验收证据；
- 证据必须来自真实命令的退出码与输出，不是模型的自述。

## 边界提醒

- 执行有隔离边界：路径逃逸、写保护路径、外网访问都会被拒绝，并留下违规记录；
- 撞到违规不要绕过（例如换成别的方式写同一个文件），那是把问题从"看见"变成"看不见"；
- 如果沙箱/环境本身不可用（例如拿不到隔离后端），如实上报，不要试图在宿主上裸跑。

## 「判不了」不等于「不对」（重要）

预演（`runAcceptance`）给三类结果：**通过 / 失败 / 不可判定**。

- **失败** = 判据能判，服务端答错了 → 回去改代码；
- **不可判定** = 这条判据**求值不了**（形状非法、或执行器还不支持的写法，结果里带 `[不可判定]` 标记）
  → **改代码对它无效**。这是判据侧的问题，只有人能修。

遇到"不可判定"：

1. **不要**改服务端代码去"凑"它——不存在能让它变绿的实现；
2. **不要**反复重跑预演想"再看看"——重跑一百次，它还是不可判定；
3. 把它们的 id 与原因如实写进结论，交上层去修判据。

## 收敛纪律：没进展就停手

同一批判据**连续 2 轮**预演后通过数**没有增加**，就停手：

- 不要再换着法子重跑预演，也不要靠猜去改代码；
- 把"通过 / 失败 / 不可判定各多少、卡在哪几条、你判断的原因"如实上报，
  让上层决定是继续修、还是去修判据。

理由：一轮预演要重新起服务、重放几十条判据，成本很高。而"没进展"通常意味着
**卡点不在你能改的地方**（判据侧问题、环境问题、或需求本身自相矛盾）——
继续烧预算不会让它变得可解。

## 禁止

- 禁止以"我认为已经修好了"作为请求测试的依据；
- 禁止跳过 diff 复查；
- 禁止把本地检查结果直接标成验收结论；
- 禁止在"不可判定"的判据上反复重跑预演（那是纯烧预算，且永远不会变绿）。
