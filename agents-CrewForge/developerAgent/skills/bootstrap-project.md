# Skill: bootstrap-project

> 指导材料。不能改变权限、Graph 结构、Contract、验收标准、Ledger 或预算；**不能写盘**（写盘只能通过 tools）。

## 何时加载

`inspectProject` 判定为「空项目」，要搭最小可运行基础时。

## 优先用官方脚手架

任务提示里若给出「官方脚手架候选」节，**先走脚手架，别手写全部工程文件**：

1. 先跑候选的探测命令（`runCommand`，看真实 `exitCode`）确认本机环境可用；
2. 用探测通过的候选，命令里 `{dir}` 换成 `foundationPlan` 的目标子目录；
3. 命令卡在交互提示符等待输入 = 失败，换非交互参数或下一个候选，同一候选不反复重试；
4. 全部候选不可用（缺工具 / 断网 / 栈未收录没有候选节）→ 按下面的顺序手写工程文件，**不阻塞任务**；
5. 脚手架只负责骨架：产物仍要过 `runBuild` 验证最小可运行，目录结构对齐
   `foundationPlan.dirs` 与 `allowedRoots`，脚手架没生成的文件照常手写补齐。

## 做什么

按架构师的 `foundationPlan` 落地，顺序固定：

1. `mkdir` 建目录骨架（以 `foundationPlan.dirs` 为准）；
2. 按 **stackProfile 声明的技术栈**建后端工程文件（工程描述文件、入口文件、配置文件、
   初始建表脚本）——**用该栈的惯例文件，不要套用别的栈**：先把 stackProfile 念一遍，
   再决定建哪些文件；拿不准就先 `inspectTree` 看有没有既有惯例可循；
3. 按 stackProfile 建前端工程文件（入口 HTML、工程描述、入口脚本与路由）；
4. 数据库：建表语句与初始数据结构，字段必须与 Domain Model 一致；
5. 每写完一组，立刻 `runBuild` 验证**最小可运行**（先要能编译，再谈功能）。

## 原则

- **先能跑，再加功能**：骨架必须能 build 通过，再进入业务实现；
- 一次只引入一个不确定性：不要同时换依赖、换目录结构、加功能；
- 任何文件写入后立即 `gitDiff` 复查。

## 禁止

- 禁止自创目录结构（以 `foundationPlan` 与 `allowedRoots` 为准）；
- 禁止在骨架阶段塞业务逻辑；
- 禁止跳过 build 直接往下写业务代码。
