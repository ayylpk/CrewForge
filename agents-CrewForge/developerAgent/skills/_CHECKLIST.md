# SKILL 自查清单（testAgent 版 → developerAgent skills 落地）

> 改任何 skill 前逐条过。核心铁律：**正文每条规范必须能追溯到一次真实发生的失败**
> （实录出处，如【实录 s4·批量重写】）。凭空列的禁止项不要写——模型对"没发生过的禁令"
> 天然不遵守，还会稀释有出处的红线。

| # | 检查项 | 过线标准 | 本仓先例 |
|---|---|---|---|
| 0 | **每条规范有出处** | 红线/禁止项都能指到一轮实弹的失败实录（p7 / s4 / s4c / s4d / s5 系列）；纯偏好型约定必须显式标注"偏好型，无失败实录，酌情采纳" | backend-development.md 数据访问节 |
| 1 | **红线 vs 偏好分档** | 硬禁止（红线）只放有实录的；偏好型不冒充红线——模型对红线密度敏感，掺假会稀释全部 | 同上 |
| 2 | **可执行性** | 规范写的是模型当轮能做的事（读什么、跑什么命令、按什么顺序），不是抽象态度 | debugging 第 0 步"先跑红色回路" |
| 3 | **渐进披露** | 正文 ≤100 行目标；机器可查的细节放引擎/工具层（如 FS_NOT_OBSERVED 拒写），不靠提示词重复 | backend-development 批量禁令引工具层 |
| 4 | **引擎护栏优先** | 提示词只解释"为什么"；能下沉为代码闸的（先读后改、契约只读、验收资产只读）不写成文字禁令 | anti-spec-gaming 十条禁令 + workspace 拒写 |
| 5 | **加载时机是谓词** | "何时加载"写成可观察条件（"收到 test_failure 进入修复循环时"），不是"需要时" | 各 skill 何时加载节 |
| 6 | **评测挂钩** | 改 skill 后必须用 eval 场景重跑验证（s 系列），skill 改动与实弹结果一起归档 | eval/scenarios/ + baseline/runs/ |
| 7 | **退休分类** | 补能力型（引擎修好即退役，如"each 断言修复后对应禁令"）vs 偏好型（长期）；红线型退休压力小 | 待办：引擎护栏覆盖后删除对应禁令 |

## 修改流程

1. 实录登记：先在 `.workbuddy/memory/` 当日日志里记下失败原文（哪轮、什么现象、根因）；
2. 从实录提炼规范（问题 → 根因 → 一条可执行的动作约束），标注【实录 <轮次>·<现象>】；
3. 过上表 → `bunx tsc --noEmit` → 相关 eval 场景重跑 → 实弹结果回填本文件"本仓先例"列。
